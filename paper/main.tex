\begin{center}
{\sffamily\bfseries\small ABSTRACT}
\end{center}
\vspace{-0.5em}
\noindent{\small
A capability token says an agent may do a thing. A signature says which bytes
it asked for. Neither says what the endpoint then did. We call the space
between the authorized message and the performed effect the \emph{effect
binding gap}, and this paper is about when it can be closed and when it
cannot. We open with a case where every component behaves correctly and the
composition is still wrong: a network retry over a non-idempotent operation,
where one branch tells the client the operation failed while the state changed
anyway, and the other executes it twice. No message-level mechanism resolves
this, because the distinction between an adversarial replay and an
infrastructure retry does not exist at the message layer. We then state four
conditions---parameter completeness, representation injectivity, strict
idempotency with nonce-decoupled retries, and contextual state
pinning---which together are \emph{sufficient} for an authorized message to
determine its effect, and we are careful to say that we have not shown them
necessary. We built a harness, \transit{}, that checks them: a parameterized
JSON decoder that reproduces the disagreements between real language runtimes
and is falsified against those runtimes; a deliberately hostile endpoint with
individually switchable failure modes; and an enforcing reverse proxy that
closes representation injectivity at the boundary, closes parameter
completeness where it is configured to, and---we say this plainly---does not
close alias collapse at all, because no proxy can. Finally we re-examine a
24-endpoint documentation survey we inherited, and report that its own table
does not support the percentages its prose reports. The corrected split is
4~/~7~/~13 rather than 4~/~6~/~14. We report that as a finding about the
method, not a rounding fix: it is a convenience sample classified from
documents, and 54\% is not a population estimate any more than 58\% was.}

\section{The Problem}
\label{sec:problem}

Start with a case where nobody makes a mistake.

An agent holds a capability token. The token is scoped, short-lived, and
carries a one-time nonce so it cannot be replayed. The agent asks an endpoint
to place an order. It signs the request bytes. The endpoint verifies the
signature, checks that the nonce has not been seen, commits the order, and
begins writing a response.

The connection drops.

Somewhere between the endpoint and the agent---a load balancer, a service
mesh, a client library with a sensible default---something decides to retry.
It has two choices, and both of them are wrong.

If it retries with the same nonce, the endpoint sees a nonce it has already
consumed and refuses with \texttt{409 Conflict}. That is exactly the right
behaviour against a replay attack. But this was not a replay; the order is
already committed. The client is now told the operation failed, and the
operation happened.

If instead the client obtains a fresh nonce and retries, the endpoint sees a
legitimate, correctly signed, never-before-seen request and commits the order
a second time. Two orders. One intent.

Every step here is individually correct. The signature check is correct. The
nonce check is correct---it is doing precisely the job replay protection
exists to do. The retry is correct; retrying a failed request is what
reliable transports are for. The composition is broken anyway, and it is
broken in a way that no amount of care at the message layer will fix, because
the message layer cannot see the difference. An adversarial replay and an
infrastructure retry are, at the level of bytes on a wire, the same event.
The distinction lives in intent, and intent is not in the message.

This is the shape of the whole problem. We will call the property we want
\emph{effect binding}: that an authorized message determines the effect
performed. What the retry case shows is that message authorization---the thing
capability protocols actually provide, and provide well---does not deliver it,
and cannot be patched into delivering it by strengthening the message.

There is a remedy, and it is worth naming now because it is the shape of every
remedy in this paper. Decouple the business idempotency key from the
authorization nonce. Let the client carry a key that names \emph{the order},
constant across retries, while the nonce names \emph{the request} and changes.
Then the fresh-nonce retry arrives with a key the endpoint has already seen,
and the endpoint returns the cached result of the first execution instead of
performing a second one. ISO~20022 has had this for years in the form of the
end-to-end identifier~\cite{iso20022}; HTTP has it as the
\texttt{Idempotency-Key} header. It closes one horn.

It does not close the other. If the first response never arrives, the client
still does not know whether the effect happened. It can ask---but asking is a
second message, and the answer to it can be lost too. What remains after every
endpoint-side fix is applied is a residual: a committed operation that the
client believes failed. We report it separately from the findings throughout,
because a conformant endpoint that shows no findings has not made this go
away, and printing ``no findings'' over it would be the paper claiming
something the paper does not believe.

\subsection{The adversarial companion}

The retry case is what goes wrong when nobody is attacking. Here is what goes
wrong when someone is.

An authorization service and an endpoint both parse JSON. They are written in
different languages, as services in a real deployment usually are. Consider:

\begin{lstlisting}
{"to":"acct-1","amount":100,"to":"acct-9"}
\end{lstlisting}

The key \texttt{to} appears twice. RFC~8259 permits this and says nothing
about which value wins; RFC~7493 (I-JSON) forbids it
outright~\cite{rfc8259,rfc7493}. Real decoders therefore disagree, and they
disagree silently. Go's \texttt{encoding/json} keeps the last occurrence.
Erlang/OTP's \texttt{json} module, which Elixir uses, keeps the first. Both
are defensible readings of an underspecified document.

So the authorization service reads a transfer to \texttt{acct-1}, applies its
policy, and signs. The endpoint reads a transfer to \texttt{acct-9} and
executes it. The signature verifies. The bytes were not altered in transit.
The authorized message and the performed effect differ, and every component
did what it was documented to do.

This is a parser differential~\cite{kaminsky2010}, and the family is old:
HTTP request smuggling is the same failure between a front-end and a back-end
that disagree about where a request ends~\cite{linhart2005,kettle2019}. What
is new is the setting. When a human clicks a button, the button and the
handler are usually the same program. When an agent signs a request, the
signer and the executor are usually not.

\section{What Others Have Built}
\label{sec:related}

\paragraph{Complete mediation, and the assumption inside it.}
Saltzer and Schroeder's design principles put complete mediation
first: every access to every object must be checked~\cite{saltzer1975}. The
reference monitor concept it formalizes~\cite{anderson1972} carries an
assumption that was so obviously true in 1972 that it did not need stating---%
the monitor and the resource are the same machine. The monitor inspects the
request and the machine performs it, and there is no gap between them because
there is no distance.

Capability protocols distribute that monitor. The authorization decision
happens in one process, on one host, in one language; the effect happens in
another. The gap the original model defined away is exactly the gap this
paper is about. Complete mediation is not wrong; it is silent on the case
where mediating and performing are done by different programs that must agree
about what a request says.

\paragraph{Capabilities.}
The lineage runs from Dennis and Van Horn~\cite{dennis1966} through Levy's
survey~\cite{levy1984} to macaroons~\cite{birgisson2014}, which add
contextual caveats a bearer can attenuate but not widen. Macaroons are a good
answer to \emph{what may be requested}. They say nothing about what the
receiving endpoint does with the request once it parses it, and the caveat
language has no vocabulary for effects.

\paragraph{Formal methods for the message layer, and only that layer.}
The Dolev--Yao model~\cite{dolevyao1983} and the tools built on
it---ProVerif~\cite{blanchet2001}, Tamarin~\cite{meier2013}---are the right
instruments for reasoning about protocol messages under an active attacker,
and they are very good ones. We want to be precise about their scope, because
it is easy to overread a green checkmark. A Tamarin proof that a capability
protocol is secure is a statement about messages: which ones an attacker can
produce, which secrets stay secret, which agreements hold. It is not evidence
about effects. The endpoint's parser, its defaulting behaviour, and its
persistence layer are outside the model, and the retry case in
Section~\ref{sec:problem} is invisible to it: both branches are protocol-legal.

\paragraph{The confused deputy.}
Hardy's compiler~\cite{hardy1988} was tricked into using its own authority on
behalf of a caller who lacked it. The structure is the same one here: a
component with authority acts on a request whose meaning it has mis-attributed.
The difference is where the ambiguity lives. Hardy's deputy was confused about
\emph{whose} authority applied; ours is confused about \emph{what was asked}.

\paragraph{Canonical form.}
RFC~8785 (JCS) specifies a canonical serialization for JSON~\cite{rfc8785},
and RFC~7493 profiles the subset over which that is
well-defined~\cite{rfc7493}. Together they are the strongest available answer
to the duplicate-key differential, and one of our practical conclusions is
simply that authorization pipelines should decode strictly and canonicalize
before verifying a signature rather than after.

\paragraph{RFC 9110.}
HTTP's own definitions of safe and idempotent
methods~\cite{rfc9110} are load-bearing for condition C3 below: a \texttt{PUT}
is idempotent by method, and a \texttt{POST} is not, and the specification
says so normatively rather than by convention.

\paragraph{ISO 20022, read closely.}
Of everything in this section, ISO~20022~\cite{iso20022} is the strongest
existing answer, and it is worth reading rather than citing. Its
\texttt{pain.001} credit transfer has a mandatory closed schema, so there are
no optional parameters for a server to fill in; it binds an end-to-end
identifier that is distinct from any transport-level retry mechanism; and
the identifier is required rather than optional. That is three of our four
conditions, met by a message format designed in the 2000s for a domain that
could not tolerate the alternative. It is proof that the conditions are
achievable in practice. It is also, notably, not a general-purpose web API.

\section{Writing It Down Precisely}
\label{sec:conditions}

Model an endpoint as a state transformer. Let $\Sigma$ be the endpoint's state
space, $W$ the set of wire representations (byte strings), and $O$ the set of
observable outputs. Parsing is a partial function $P : W \rightharpoonup D$
into documents, and the endpoint is

\[
E \;:\; \Sigma \times W \;\to\; \Sigma \times O .
\]

Write $E$ as the composition $E(\sigma, w) = X(\sigma, P(w))$, where $X$
performs the effect on a parsed document. The authorization service holds its
own parser $P'$ and a policy $\Pi$ over documents, and signs $w$ when
$\Pi(P'(w))$ approves.

\begin{definition}[Message authorization]
A deployment provides message authorization if no party can cause the endpoint
to accept a wire representation $w$ that was not signed by an authorized
holder.
\end{definition}

\begin{definition}[Effect binding]
A deployment provides effect binding if, for every authorized $w$, the
resulting state transition and output $E(\sigma, w)$ are determined by
$P'(w)$---the document the policy evaluated---and by nothing else.
\end{definition}

The two are independent. The retry case has message authorization and lacks
effect binding. That is the whole point.

The four conditions below are each pinned to code that checks them, in
\texttt{src/classify.rs} of the accompanying implementation.

\begin{description}[leftmargin=1.6em, style=nextline]
\item[C1 --- Parameter completeness and default invariance.]
Every input that influences the effect appears in the signed document.
Formally, $X(\sigma, d)$ does not read any component of $\sigma$ that a
client could have specified but did not. The failure mode is a server-side
default: an omitted \texttt{fee\_tier} filled in from account state, so the
policy approves an ordinary transfer and the endpoint performs an expedited
one. Checked by \texttt{judge\_c1}.

\item[C2 --- Representation injectivity.]
$P$ and $P'$ agree, and each is injective on the meanings it admits: two wire
forms that parse to one document must not exist, and one wire form must not
parse to two documents under two parsers. The duplicate-key case violates the
second half; a resource reachable as both \texttt{/v1/users/me} and
\texttt{/v1/users/usr\_99812} violates the first. Checked by
\texttt{judge\_c2}.

\item[C3 --- Strict idempotency with nonce-decoupled retries.]
Repeated delivery of one authorized document produces one effect, and the
identifier that establishes ``one document'' is distinct from the nonce that
establishes freshness. Checked by \texttt{judge\_c3}, which treats the
methods RFC~9110 defines as idempotent as satisfying it by construction.

\item[C4 --- Contextual state pinning.]
Where the effect depends on state that can move between signing and
execution, the document names the state it assumes, and the endpoint refuses
if that assumption no longer holds. An \texttt{If-Match} precondition is the
ordinary spelling. Checked by \texttt{judge\_c4}.
\end{description}

\section{Sufficient, and Not Known To Be Necessary}
\label{sec:sufficiency}

We claim that C1--C4 together are sufficient for effect binding. We do not
claim they are necessary, and we want to be explicit about that because the
source material we build on is not.

The desk study that preceded this work states its restated theorem as an
``if and only if'' while establishing one direction. That is an overstatement,
and it is the kind a reviewer will find first.

Sufficiency is the direction that carries the engineering weight. If every
effect-relevant input is in the document (C1), the document has exactly one
wire form and one meaning (C2), redelivery cannot multiply the effect (C3),
and the assumed state is pinned (C4), then the effect is a function of the
document the policy evaluated, which is what Definition~2 asks for.

Necessity is open, and there are concrete reasons to doubt it. An endpoint
could achieve effect binding by co-locating the monitor with the resource, in
which case the reference-monitor assumption holds again and none of C1--C4 is
needed as a message-level property. An endpoint whose effect is a total
function over a fixed state space satisfies Definition~2 without pinning
anything, because there is no state to move. Neither of these is exotic.

The distinction matters for a standard rather than only for a proof. A
standard that mandates C1--C4 as necessary conditions would refuse to certify
deployments that are, in fact, effect-binding by other means---and would tell
an implementer that a co-located monitor is insufficient when it is not. We
therefore state the conditions as a sufficient set and a conformance target,
and we mark the necessity direction as open work.

\section{How We Checked}
\label{sec:method}

The harness, \transit{}, has three parts, and the relationship between them is
the methodological argument.

\paragraph{One decoder, many behaviours.}
Rather than depending on five language runtimes being installed, we wrote a
single JSON parser parameterized by the decisions real decoders make
differently: duplicate-key policy, lone surrogate handling, number range,
Unicode normalization. Each configuration is a \emph{model} of a runtime, and
a model is a claim. So we falsify them: where a runtime is present on the
host, we run the same corpus through it as a subprocess and require the model
to agree. Where a runtime is absent, the model still runs and the output
labels it \texttt{Unverified}, in every format, on every row.

We state one substitution plainly. The canonical pair in the literature is
Go's last-key-wins against Elixir's first-key-wins. No Elixir runtime exists
on our development host. The acceptance test therefore asserts the divergence
between two decoders that are genuinely present and independently
written---a strict I-JSON decoder and \texttt{serde\_json}---and exercises
first-key-wins through the Elixir model, labelled \texttt{Unverified}.
First-key-wins on OTP~27 has since been measured directly on a separate
machine, and that measurement is recorded as a fact about that machine. The
local decoder remains a model regardless, and says so.

\paragraph{A hostile endpoint, as a pure function.}
The endpoint under test is a function from state and request to state and
response, with five failure modes that switch independently: lenient
decoding, profile defaulting, URI aliasing, non-idempotent handling, and
absent state pinning. The same function serves over HTTP and runs in-process,
so the tests that matter need no socket and cannot flake.

Turning every failure mode off gives the \emph{boundable profile}, and it is
the control. A check that produces a finding against the hostile
configuration and nothing against the boundable one is evidence about the
endpoint. A check that fires against both is evidence about the checker. Every
acceptance test in the harness runs both halves for exactly this reason: a
checker that returned a constant would pass the first half and fail the
second.

\paragraph{An enforcement point, and its ceiling.}
The last part is a reverse proxy that strict-ingests every request and
forwards the canonical form rather than the wire form, so the upstream and the
signer cannot be reading two spellings of one document. It is the deployable
form of the argument, and its limits are as interesting as its function.
Against the three attacks the harness reproduces:

\begin{center}
\begin{tabular}{lll}
\toprule
Attack & Condition & Through the proxy \\
\midrule
Duplicate-key split & C2 & Rejected, unconditionally \\
Parameter-defaulting bypass & C1 & Rejected \emph{only if} the route names the parameters \\
URI alias collapse & C2 & \textbf{Passes} \\
\bottomrule
\end{tabular}
\end{center}

The third row is not a defect being tolerated. \texttt{GET /v1/users/me}
carries no body and its path is untouched; a proxy has no way to know that
\texttt{me} and \texttt{usr\_99812} name one resource. We assert that row as a
passing request in the test suite, so that the claim cannot quietly widen in
a later draft of the README.

\section{The Survey We Inherited}
\label{sec:survey}

The desk study that preceded this work classified 24 production endpoints
against C1--C4 and reported that 58.3\% (14 of 24) fail, 25.0\% (6 of 24) are
conditional, and 16.7\% (4 of 24) qualify.

Counting its own table gives 4 qualified, 7 conditional, and 13
non-qualifying. Square's \texttt{POST /v2/payments} is a Conditional row that
the 25\% figure omits and the 58\% figure then absorbs. The rows are right;
the arithmetic over them is not. An earlier draft of this paper repeated the
published figures.

We found this because the harness refuses to let a number be typed into the
paper. The survey lives as a data file, the counts are computed from it, and
a test asserts the split. The correction is small, but it is the discipline
working on its first application, and we report it rather than quietly
publishing the corrected figures.

The wider point is more important than the arithmetic. Twenty-four endpoints
chosen for sector coverage is a convenience sample, and a classification
derived from reading documentation is a hypothesis about implementations. C1
and C4 in particular are properties of implementations that no document
reveals: a specification cannot tell you what a server fills in from account
state, and cannot tell you whether an effect depends on state that moved. So
54\% is not a population estimate any more than 58\% was. It is a taxonomy
with illustrative cases, and every rendering of the table in this repository
carries a banner saying so---including the generated \LaTeX{}, so that the
table cannot be pasted into a paper without the caveat travelling with it.

\section{What We Still Don't Know}
\label{sec:openwork}

\paragraph{The checkability problem.}
This is the crux, and it undercuts the survey more than any sampling
objection. C1 and C4 are properties of implementations, not of published
interfaces. Absent source access, classifying an endpoint means inferring
implementation behaviour from documentation and black-box probing, and the
credibility of any survey rests entirely on how that inference is made. Our
classifier returns \texttt{Unknown} rather than a verdict wherever a document
cannot answer, which is honest but is not a measurement. Turning these rows
into evidence requires probing running endpoints under authorization, and we
have built the gate for that but not run it.

\paragraph{Verification without cooperation.}
Everything above assumes you can ask the endpoint questions. An auditor who
wants to know whether a third-party API is effect-binding, without an account
and without permission, has no method we know of that is both sound and
lawful.

\paragraph{What replaces binding where it cannot be had.}
Thirteen of twenty-four endpoints in the survey cannot satisfy the conditions
without changing their interfaces, and most of them will not. Detection after
the fact, bounded exposure, and compensating controls are the realistic
answers, and none of them is developed here.

\paragraph{Composition.}
This paper treats one authorized message and one effect. Agents perform
workflows: a sequence of calls where each step's inputs depend on earlier
steps' outputs. Whether effect binding composes across such a sequence---and
what an authorized \emph{plan}, as opposed to an authorized message, would
even mean---is untouched, and is arguably the question the agent setting
actually poses.
